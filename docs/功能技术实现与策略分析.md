# AI 银行助手 · 功能技术实现与策略分析

面向队友:逐个功能说清 ①技术实现原理 ②产品逻辑策略 ③优缺点。更新 2026-10-09 · 代码基线 a47cec5 · 与《产品功能说明》互为表里(那份讲「有没有」,这份讲「怎么做、为什么这么做、代价是什么」)。

## 零、所有功能共用的骨架

六个场景不是六套代码,而是同一套骨架换了业务节点。看懂这一层,后面每一节都只是填空。

- **一条主线** —— 消息 → router 单次意图分类 → 该场景专属管线(抽取→澄清→查数→建单) → 人工闸门(interrupt 暂停等人) → 执行 → 播报
- **策略一** —— LLM 只做「理解与表达」:金额、费率、统计、日期全部由确定性代码计算,模型不许心算
- **策略二** —— 动钱必过闸门:先建单不扣款,人工确认 + 支付密码核验后才扣(转账/理财/联动/订阅取消同款)
- **策略三** —— 一切循环都有封顶,绝不无限纠缠:反问最多 3 轮、闸门最多问 2 次、单轮总时长 180 秒、图递归上限 50
- **策略四** —— 只读场景不打扰(账单/查询零闸门),写入场景才弹卡要密码——闸门按风险分级,不是一刀切
- **策略五** —— 失败要可见:工具报错走 bank_error 如实播报,绝不静默降级成「看起来成功了」

## 一、智能转账

### 技术实现原理

- 节点管线 t_extract → t_clarify(缺槽追问) → t_resolve(姓名/手机号定位收款人) → t_disambiguate(同名时给候选让你选) → t_policy(风控预检) → t_create(建单) → t_gate(闸门) → t_confirm / t_cancel → t_report
- 动钱工具两步走:create_transfer_order 只写 pending_confirm;confirm_transfer_order 才在同一个 BEGIN IMMEDIATE 事务里改余额 + 插流水 + 置 executed,并二次校验余额与限额
- 幂等键 = sha1(会话 thread | 本轮原话 | 账户 | 收款人 | 金额分 | 定时时刻),写进 transfer_orders.idempotency_key UNIQUE——同一条指令重放命中旧单,不会二次扣款
- 定时转账:建 scheduled 单,到期只转「待确认」,永远不自动扣
- AA 收款走独立支线 sb_*(发起建账单)与 ss_*(逐人结算标记已付)
- 风控三条规则在建单和确认时各跑一次:单笔上限 5 万、当日累计转出上限 1 万(演示故意收紧,为的是现场能演示拦截)、可选白名单

### 产品逻辑策略

- 钱的安全靠流程而不是靠模型:模型只负责把「给老王转五十」翻译成结构化槽位,所有校验、扣款、留痕都在银行层用代码完成
- 宁可多问一句,不可转错一人:同名联系人必须让用户选,缺金额/缺收款人一律反问
- 确认卡片复述全部要素(收款人/金额/时间/限额),支付密码是最后一道人工闸

### 优缺点分析

| 维度 | 内容 |
|---|---|
| 优点 | 资金安全四件套齐全(两步走 / 幂等 / 限额 / 审计);同名消歧避免转错人;定时与 AA 都复用同一套闸门语义,没有旁路 |
| 缺点 | 全流程要 15–30 秒(抽取 + 闸门 + 密码核验多次模型往返);口语金额靠模型抽取,长历史下 router 偶发不输出 JSON → 安全回落成闲聊(评估 8 个转账剧本通过 6 个,均零资金风险) |
| 边界 | 只能从活期账户转出;限额为演示值,不是真实银行参数 |

## 二、账单分析

### 技术实现原理

- 节点管线 b_extract → b_clarify → b_run → b_report,全程零闸门、零动钱
- 「上个月」「最近三个月」这类口语周期由确定性代码 parse_period 换算成具体月份/天数,不交给模型
- 四个只读工具:monthly_report(月报:收支/结余/环比/储蓄率)、category_summary(分类统计)、top_merchants(Top 商户)、detect_anomalies(三条规则:重复扣款 / 大额离群 / 凌晨大额)
- 报表口径显式排除内部划转(自有账户互转、申购赎回),避免把资产调配算成消费

### 产品逻辑策略

- 财务数字是最不能容忍幻觉的地方:所有数字来自 SQL 聚合,模型只负责把结果讲成人话
- 只读即无风险,所以不给闸门——不问密码、不弹卡,用户体验优先
- 异常检测用规则不用模型:规则能给出「证据」(哪几笔、间隔多久),可核对;模型给的结论无法自证

### 优缺点分析

| 维度 | 内容 |
|---|---|
| 优点 | 数字可追溯到原始流水,天然抗幻觉;只读零风险;异常检测附带证据,不是空口结论 |
| 缺点 | 只有文本播报,没有图表可视化(前端未接图表库),汇报场合不够直观;规则识别不了复杂消费模式;依赖库里已有的历史数据 |
| 边界 | 不做预算建议、不做跨行账户聚合 |

## 三、理财操作

### 技术实现原理

- 四条支线共用 w_extract:w_query(查/对比/持仓)、w_assess(五题风险测评 → C1–C5)、w_subscribe → w_gate → w_confirm(申购)、w_redeem → w_redeem_gate → w_redeem_exec(赎回)
- 适当性闸门在银行层强制:未做测评只能买 R1(现金管理类),R2 及以上直接拒;有测评则产品风险等级 > 你的 C 等级一律拒
- 申赎同为两步走,并按 2026-10-04 补上的幂等键(agent-wealth-* 前缀)防重放,external_ref UNIQUE 兜底——同一句话重发不会二次扣款
- 费率/锁定期/业绩基准全部由产品库原样返回,卡片只是转述

### 产品逻辑策略

- 合规优先于成交:该拒就拒,不因为用户坚持而放宽——这是理财场景与转账场景最大的不同
- 把「测评」做成对话式五题,而不是跳转表单,保持「一句话办事」的产品形态
- 推荐先过滤再展示:按你的等级筛出可购产品,不展示买不了的东西,减少挫败感

### 优缺点分析

| 维度 | 内容 |
|---|---|
| 优点 | 适当性闸门硬约束,不会出现「保守型客户买 R5」;申赎幂等,重放零风险;费率数字来自产品库,不会算错 |
| 缺点 | 无实时行情,收益是预置样例;未测评用户要先过五题测评,链路偏长;产品对比曾因工具参数名不匹配而静默返回空结果(2026-10-04 已修,并补了断言) |
| 边界 | 演示产品库;不做投顾建议,只做适当性范围内的筛选与执行 |

## 四、卡片管理

### 技术实现原理

- 节点管线 k_extract → k_clarify → 按 action 分流 k_list / k_apply / k_limits / k_status → k_gate(闸门) →(挂失再加一道 k_lost_gate)→ k_exec → k_report
- 查询不弹卡;办卡/调限额/改状态过 confirm_card 闸门并要支付密码;挂失是双闸且提示不可逆
- 调限额区分日限额与单笔限额,只改传了的那一项;每次写操作都留审计

### 产品逻辑策略

- 按破坏性分级:只读 → 直接答;可逆写(限额/锁定)→ 单闸;不可逆(挂失)→ 双闸 + 明示后果
- 卡片号一律脱敏展示(6222 **** **** 8821),不把完整卡号送进对话

### 优缺点分析

| 维度 | 内容 |
|---|---|
| 优点 | 闸门强度与操作破坏性匹配,不滥用确认;挂失双闸把「不可逆」这件事讲在确认之前 |
| 缺点 | 演示环境办卡秒批,没有真实审批与制卡流程;挂失无撤销入口(刻意设计,但演示时要注意别误触);卡片数据来自种子库,不含真实权益体系 |
| 边界 | 每人预置 2 张卡;不做分期、积分、权益对比 |

## 五、订阅 / 代扣管理

### 技术实现原理

- 清单侧:种子/历史流水里用 detect_subscriptions 挖掘周期扣费——同商户、同金额出现 ≥3 次,相邻间隔方差 ≤±3 天且周期在 7–95 天之间,判为订阅;写入 subscriptions 表并算年化
- 对话侧节点管线 s_extract → s_clarify → s_list(查清单,只读发卡)→ s_report;取消走 s_extract → s_pick(按商户名定位)→ s_gate → s_exec → s_report
- 商户名定位是确定性的:先精确匹配,再尝试唯一包含匹配,都不中则如实回「没找到」
- 取消代扣过 confirm_sub_cancel 支付密码闸门,取消后写 subscriptions.status=cancelled,同时往管理台变更记录库写一条留痕

### 产品逻辑策略

- 让用户「看见自己没注意到的钱」:订阅识别不需要手动录入,直接从流水里挖,并给出月合计/年合计与涨价提示
- 取消是不可逆的协议动作,所以按敏感操作对待(要支付密码),而不是一点即销

### 优缺点分析

| 维度 | 内容 |
|---|---|
| 优点 | 零录入成本;集合了金额、下次扣费日、年化成本与涨价提示,一屏看完;取消有密码闸 + 后台留痕 |
| 缺点 | 挖掘口径缺了账单侧已有的「内部划转排除」——自有账户互转与理财申购(如「理财专户」「余额+货币基金」)会被误判成订阅,演示清单 8 条里有 2 条是伪的、年合计被抬高约 4.7 万(2026-10-09 发现,修法是复用同一过滤条件,尚未修);只能整笔取消,不能改金额或周期;识别不到的周期扣费不会出现 |
| 边界 | 只覆盖台账能看到的代扣,不代表真实商户协议 |

## 六、跨场景联动(生日剧本)

### 技术实现原理

- 建计划:l_extract(抽事件/预算/动作)→ l_clarify → l_plan → l_gate(闸门)→ l_confirm / l_cancel
- 预算锁定不是直接扣钱:create_linkage_plan 从活期向理财专户建一张 pending_confirm 的转账单,计划确认时才对这张锁定单执行 confirm_transfer_order
- 到期处理走另一条支线:l_due(找出到期动作)→ l_due_gate(逐项闸门)→ l_due_exec / l_due_skip,一次确认只买一样东西
- 每笔到期购买写 transactions.external_ref = linkage:{plan_id}:{action_idx}(UNIQUE),重复执行被数据库直接拦下

### 产品逻辑策略

- 「主动但不越权」是这个场景的核心主张:系统可以主动发现机会、主动准备、主动提醒,但每一步真正花钱都必须用户点头
- 把「记住用户生活里的事」做成结构化事件(生日/纪念日/发薪日),而不是塞进对话记忆里

### 优缺点分析

| 维度 | 内容 |
|---|---|
| 优点 | 赛题点名的高级能力,链路完整:识别 → 锁预算 → 定时提醒 → 逐项确认购买;每一环都留了人工出口,资金零自动支出 |
| 缺点 | 没有常驻调度器,到期靠「有人打开网页」触发(演示靠「演示快进」按钮拨日期);只对生日剧本做了专门优化,其他事件类型数据结构支持但对话入口未打磨 |
| 边界 | 演示沙箱内的联动,不对接真实日历与电商 |

## 七、横切机制(所有功能共用)

| 机制 | 技术原理 | 策略 / 代价 |
|---|---|---|
| 意图路由 | router 单次 LLM 调用输出 JSON,白名单 10 类意图;解析失败或未知一律回落 chat | 策略:宁可答非所问,绝不误碰银行。代价:长历史偶发不输出 JSON,被当成闲聊(2026-10-09 评估 3 条失败同根,均零资金风险) |
| 人工闸门 | LangGraph interrupt 暂停 + 状态计数封顶(gate_round ≥ 2 一律按取消) | 策略:钱的事必须人点头,且模糊答复等于拒绝(只认无保留的肯定)。代价:异步节点拿不到 config,thread_id 要从 get_config() 取;闸门节点只能有一个 interrupt 调用点,两个会无限重问 |
| 缺槽反问 | clarify 节点自环,最多 3 轮,超限给 gaveup 收尾 | 策略:不无限纠缠。代价:3 轮没问出来就结束本次办理,用户需重新发起 |
| 幂等防重放 | sha1(thread | 本轮原话 | 业务要素)作键,DB UNIQUE 兜底 | 策略:同一条指令重发不产生第二笔。代价:键含「原话」,换个说法表达同一意图会被视为新一笔(刻意取舍,避免误伤真实的新交易) |
| 全量审计 | 每次工具调用写 audit_log(入参/结果/风险级别);另有两本独立记录库(资金流水 + 功能修改)供管理台查询,操作方可区分 agent/admin | 策略:一切可回放、账实可对;支付密码在留痕时脱敏为 ***。代价:audit_log 无索引也无用户列,数据量大后查询会变慢(尚未优化) |
| 会话记忆 | LangGraph AsyncSqliteSaver 存消息,独立 threads 库存会话目录(单一事实来源,不重复存内容);待确认问题存在目录里而不是写图状态 | 策略:刷新页面、换浏览器都能恢复现场。代价:检查点库会持续膨胀,目前没有清理/归档策略 |
| 流式协议 | SSE 按 Vercel AI SDK UI Message Stream 输出,自定义部件统一 data-* 前缀,现有 13 种;图节点载荷 → api 映射 → 前端组件三层 | 策略:前端 useChat 零胶水即可消费;新增部件有契约守卫测试自动红灯。代价:加一种卡片要同时改三处,漏一处就静默不显示 |
| 工具层解耦 | 银行能力全部做成 MCP 工具(42 个,stdio),按登录用户注入子进程环境变量 | 策略:编排层与银行层解耦,任何 MCP 客户端都能复用这套银行能力;天然按用户隔离。代价:每次工具调用新起一个子进程,有固定启动开销,链路长、调试不如同进程直观 |

## 八、一句话总结

这套系统的产品策略可以概括成一句话:**让模型负责「听懂人话」,让代码负责「守住钱」**——凡是涉及金额、状态、权限的判断都下沉到确定性代码,凡是涉及资金变动的动作都留一个人工闸门,凡是可能失败的地方都让失败可见。代价是流程更长(动钱要 15–30 秒)、部分场景牺牲了即时性(定时与联动不自动执行),换来的是演示现场「怎么问都不出事」的可预期性。
