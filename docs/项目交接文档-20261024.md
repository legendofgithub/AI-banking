## 一、这个项目是什么

2026 深圳国际金融科技大赛 · AI Banking Agent 赛道作品：**对话式银行助手**。
用户在聊天窗口说"给老王转 500""帮我分析上个月账单""帮我准备生日"，Agent 理解意图后
调用银行能力层办理；**一切动钱操作先建单、人工确认 + 支付密码后才扣款**。
演示主用户"陈明"，含生日惊喜、订阅省钱、账单分析等演示剧本。

## 二、交接清单（接手当天照做）

### 2.1 首次部署（clone 路线，勿用 zip 拷贝）

```text
前置：装 Git、Python 3.12+、Node.js LTS（含 pnpm）
1. git clone https://github.com/legendofgithub/AI-banking.git   # 公开仓库，https 即可
2. 双击 启动演示.bat
   → 首次运行自举：生成 webui/.env.local（提示粘贴 API Key）→ 建 .venv 装依赖
   → pnpm install → 播种 data/bank.db → 起四个服务 → 自动开浏览器
```

**为什么不用 zip**：磁盘上的 `.venv`/`node_modules` 绑死本机路径（拷过去必废）、
`data/*.sqlite` 是原机器的运行现场（测试脏数据）、`.env.local` 里有 Key；
而 clone 只拉 4MB 源码——依赖有 `requirements.txt`/`package.json` 配方可重建，
数据有 `bank_core/seed.py` 自动播种，密钥被 `.gitignore` 挡在库外。

**唯一必填项**：`webui/.env.local` 里的 `ZAI_API_KEY`（当前配的是 DeepSeek 端点 +
`ZAI_MODEL=deepseek-chat`）。给接手人两个选择：① 临时用作者的 Key；② 自备 DeepSeek Key
（推荐，作者随后在 DeepSeek 后台轮换旧 Key）。也可以在界面「设置 → 大模型管理」里填
BYOK（自带 Key/端点/模型，随请求生效，不动服务端配置）。

### 2.3 日常运维

- 重播种（重置演示数据）：先停服务占用的库，再 `.venv/Scripts/python.exe -m bank_core.seed`
- 清理进程：**先 `netstat -ano` 查 PID 再按 PID 杀**，绝不 `taskkill /IM node.exe` 全杀
- 内存紧张（16GB）：webui 只用 `next build + next start`，**禁 `next dev --turbo`**（必 OOM）
- 交付铁律：改完必须 commit；必须跑全量 `.venv/Scripts/python.exe -m pytest tests -q`
  （当前 392 例，进程内 MCP 替身，约 60s）；动钱链路改动必须浏览器实走一遍
- GitHub 推拉走 SSH:443（`~/.ssh/config` 已配），HTTPS 时通时断别死磕

### 2.4 已知环境红线（踩过的坑，别再踩）

1. `requirements.txt`/`requirements.lock.txt` **保持纯 ASCII**——中文 Windows 下 pip 用
   GBK 读文件，含中文注释会 UnicodeDecodeError、一个包都装不上
2. 重启后端必须用 venv python；系统 Python312 没装依赖（服务能起是假象，重启必挂）
3. 只换 Key 不换 `ZAI_BASE_URL` 会变成"DeepSeek 的 Key 打到智谱端点"的必挂组合——
   `启动演示.bat` 已把 `ZAI_*` 三变量一起从 `.env.local` 回填
4. 手机扫码演示需要手机与电脑**同一局域网且路由器不隔离设备**——eduroam 等校园网
   开设备隔离，扫出来"无法打开页面"；换手机热点最稳

## 三、架构总览（10 分钟版）

### 数据流

```text
用户消息(webui 3000)
  → POST 8800 /api/chat (SSE 流式)
    → router: LLM 意图分类(十选一, 输出 JSON)
    → 分流:
       含分析触发词(分析/复盘/规划…) → a_* Agent Core 链(感知→规划→守卫→执行→复盘→播报)
       业务意图                       → 对应子图(t_/sb_/ss_/c_/l_/p_/b_/w_/k_/s_ 前缀)
                                        抽取→缺槽反问(interrupt 等人)→查数→建单→闸门→执行→播报
       其余                          → chat 闲聊
    → 每步经 astream messages/updates 双通道发 SSE 帧:
       text-delta(播报流式) / reasoning-*(思考流) / data-*(卡片契约) / gate interrupt
  ← 前端按帧类型渲染: 流式文本 / 思考面板 / 分析卡/确认卡/选项卡(点按钮=回话继续)
```

### SQLite 五库（各管一摊，物理隔离）

| 库 | 内容 | 忘记忆会不会碰 |
|---|---|---|
| `data/bank.db` | 银行事实：账户/流水/订阅/持仓/审计/账号 | 否 |
| `data/agent_ckpt.sqlite` | LangGraph 检查点=短期记忆（整会话消息+闸门现场） | 否 |
| `data/agent_threads.sqlite` | 会话目录/跨设备同步游标/消息投票 | 否 |
| `data/agent_memory.sqlite` | 长期记忆五模块 | **就是它** |
| `data/agent_persona.sqlite` / `agent_tasks.sqlite` | 人设 / 长程任务 | 否 |

### 三条资金安全铁律（评审核心，动钱代码必须遵守）

1. **两步走**：建单（pending_confirm，零资金变动）→ 确认（同一事务扣款+流水+置 executed）；
2. **幂等防重放**：`sha1(会话|原话|账户|收款人|金额|时刻)` 入 UNIQUE 键，重放命中旧单不二次扣款；
3. **闸门分级**：写入型操作（转账/理财申赎/订阅取消/联动锁预算）必过 interrupt 人工确认，
   动钱再叠加 6 位支付密码核验（4 次锁转账功能，仅管理员可解）；只读查询零打扰。
   另有全量审计日志（audit_log + bank_calls 轨迹）与风控限额（单笔 5 万/日累计 1 万演示值）。

## 四、能力全景：功能 → 技术原理 → 产品策略 → 优缺点

### 4.0 六大业务场景（速览，深讲见旧文档）

| 场景 | 子图前缀 | 闸门 | 一句话现状 |
|---|---|---|---|
| 智能转账/定时 | t_ | 确认+支付密码 | 最成熟；幂等/消歧/风控齐全 |
| AA 收款/结算 | sb_/ss_ | 确认 | 依赖账单上下文 |
| 收款人录入 | c_ | 确认 | 引导式三槽位 |
| 跨场景联动 | l_ | 锁预算密码 | 生日剧本的执行器 |
| 生日预算计划 | p_ | 确认+密码 | 只读规划→复用 l_/s_ 执行 |
| 账单/理财分析 | b_/w_ | 无（只读） | w_ 申购赎回过 confirm_wealth |
| 卡片管理 | k_ | 挂失双闸 | 挂失不可逆故双确认 |
| 订阅/代扣 | s_ | 取消要密码 | 反问选项卡是样板间 |

### 4.1 Agent Core（一个 Core + 六技能）——2026-10 中旬新增

**技术原理**：`agent/core.py` 定义 Plan（目标/约束/步骤/闸门/成功条件/trace 的冻结 JSON）、
Guard（静态校验：越权步骤/违反约束直接拦下，零执行）、拓扑序执行器、Observe-Reflect
（对照成功条件复盘）、重规划 diff（改了什么必须可见）。`agent/skills.py` 把 44 个底层工具
收敛成 **6 个技能**（analyze_bill/analyze_wealth/plan_birthday + 三个 execute_* 资金技能），
每个声明工具白名单/风险/幂等/闸门/成功条件；**Core 只能自主跑两个只读分析技能**，
资金技能在 `run_skill` 里被显式拒绝、强制走既有受闸门子图。
路由分流是确定性的：消息命中 `_ANALYSIS_TRIGGER_WORDS`（"分析/复盘/规划/怎么省…"）才进
a_ 链（`graph.py:837`），其余照走旧子图——**零新增 LLM 调用**（只有收尾播报一次）。

**产品策略**："Agent 本身"叙事——演示有规划-执行-复盘-记忆闭环的自主感，同时资金类
保持傻瓜式执行不冒险。计划卡（data-analysis-plan）展示目标/统计期间/事实行/计划步骤/
复盘结论/上次记忆，全程可回放。

**优缺点**：

| 优点 | 缺点 |
|---|---|
| 自主感与安全兼得：只读技能才许 Core 自跑，资金零旁路 | 分流靠触发词，措辞敏感：说"看看持仓"走旧 w_ 子图不写记忆，说"分析持仓"才进 Core——口径不一致 |
| 纯确定性编排（零额外模型调用），快且可回放 | 技能=写死的工具编排，不是 LLM 动态规划——"自主"是演示叙事，泛化到新目标需改代码 |
| Plan Trace + 复盘 diff 全程可见，答辩可讲性强 | Guard 只做静态校验，无运行时预算/步数约束（有 recursion_limit 兜底） |

### 4.2 三层记忆 + 「Agent 记忆」弹窗——2026-10-22/23

**技术原理**：短期记忆=LangGraph checkpointer（`agent_ckpt.sqlite`，按 thread_id 持久化
整会话+闸门 interrupt 现场）；工作记忆=AgentState（30+ 键的 TypedDict，九套业务槽位/
候选/订单/闸门轮次）；长期记忆=`agent_memory.sqlite` 五模块白名单
（profile 画像 / bill / wealth / birthday 技能经验 / plan_history 队列限 5 条）。
写：a_ 复盘节点 merge 经验+追加计划历史（`graph.py:3524-3570`）、路由器确定性捕获
"我叫X"写 profile.name、生日闸门写 birthday 经验；读：a_perceive 用
`summarize_for_plan`（纯字符串拼接，零 LLM）注入计划卡与思维链，闲聊注入称呼。
全部 UPSERT（每模块每用户只留最新一条）、WAL 防锁库、失败软处理留痕不炸主流程。
用户自服务：webui「设置 → Agent 记忆」弹窗可看可忘（单档 `DELETE /api/memory/{module}`、
全部 `DELETE /api/memory`、结束任务 `/api/memory/active-task`——字面路由必须先于
通配注册）。**忘记只删记忆库**，任务/人设/会话检查点/投票各在独立库物理隔离，实测零误伤。

**产品策略**：记忆是"下次更有用"的经验而非聊天记录；用户对记忆有完全控制权
（看得见每一档、随时可忘、忘了会重新学）；"上次记忆"行展示在计划卡上让联动可见。

**优缺点**：

| 优点 | 缺点 |
|---|---|
| 五库隔离+软失败，记忆挂了绝不拖垮主流程 | 无语义检索（无 embedding），按键取用、每模块单条覆盖——泛化记忆存不了 |
| 写读键名契约逐点对齐，392 测试含空库/忘记/并发事务覆盖 | "写记忆"只在 a_ 链路（见 4.1 缺点：措辞敏感） |
| 忘记→重建闭环实测通畅（忘记→分析→复盘自动重建） | 「全部忘记」连 profile.name 一起清，演示"叫出名字"前要先自我介绍 |

### 4.3 人设系统——2026-10-24

**技术原理**：`agent/persona.py` 独立 SQLite；8800 `GET/PUT /api/persona`；
`RequestLLM` 缓存键加 temperature 维度（同人设不同温度各实例化，绝不串温）；
`_persona_ctx` **只注入播报(_announce)与闲聊(chat)两个 LLM 调用点**——抽取/路由/闸门
零扰动；计划卡🎭行展示当前人设。前端「设置 → 人设」弹窗（文本+温度滑条）。

**产品策略**：用户可调教 Agent 说话风格，但"从属性规则"钉死——人设改语气，不改事实
数字、不改资金行为。温度只影响表达发散度。

**优缺点**：实现小而干净（一天落地）、作用域克制（不碰业务正确性）；缺点是只有
一个全局文本 prompt 的表达力，无人设模板/多角色，且 temperature 对非 reasoning
回答的影响用户感知有限。

### 4.4 跨设备同步（手机↔电脑）——2026-10-21，10-24 修 bug

**技术原理**：服务端每用户维护 `active_threads`（当前会话）+ threads.revision（内容版本）。
前端 1.5s 轮询 `/api/sync/state`；另一台设备打开会话时 POST `/api/sync/active` 登记，
本机轮询到**服务端 active 值发生变化**才 `router.push` 跟随，revision 变化才回拉历史；
自己设备写的更新（last_client_id 相同）不回拉，防打断本地流式。

**产品策略**：手机扫码登录后自动落在电脑正看的会话；"多设备接力"演示点。
首页(/)不自动跟随，避免正常开新会话被拽走。

**教训案例（2026-10-24 修复）**：初版逻辑是"服务端 active ≠ 本地就跳"——新会话首条
消息还在后端排队（thread 行未落库，登记返回 ok=false）时，2.5s 保护窗一过就被弹回
旧会话，表现为"点账单分析白屏一下弹回首页"。修复=只跟随 active 的**变化**而非
**差异**（`webui/hooks/use-device-sync.ts`，lastSeen 游标）。接手人记：**跟随类功能
必须以"远端值变化"为信号，不能以"与本地不同"为信号**。

**优缺点**：无长连接、实现轻（轮询+两个接口）；1.5s 轮询有延迟且空耗，个人演示
量级够用、并发用户多时该改 SSE/WebSocket。

### 4.5 深度思考流（原生 reasoning）——2026-10 中旬

**技术原理**：可见答案（播报/闲聊）用 `strong=True` 调模型，`RequestLLM` 按
`thinking_model_for` 换推理模型（DeepSeek：chat→reasoner；GLM：同模型带 thinking 字段）；
reasoner 的 `reasoning_content` 逐 token 经 ChatDeepSeek 进 additional_kwargs，
api.py 的 messages 通道捕获后以 `reasoning-start/delta/end` 帧下发（60 字符合帧防轰炸），
收尾存 threads.last_reasoning 供刷新恢复。reasoner 调用失败（欠费/超时）自动回落
快模型重试，保证有答案。前端"Thought for…"折叠面板流式展开。
注意：确定性思维链面板 data-thinking（人设→识别意图→**调取记忆**→计划→守卫→复盘）
**前端已下线渲染 null**（bank-parts.tsx:1623，契约保留防前后端集合不一致）——
后端每轮仍在生成并下发该帧，属已知残留线（见 §五 P2）。

**产品策略**：办理类问题要快（快模型），开放问题才值得"想"（reasoner）；
思考过程可视化是答辩信任感的关键演示点。

**优缺点**：双模型分级+失败回落很稳；缺点：reasoner 偶发对简单转述任务不产出
思考（面板不出现，属模型行为非故障）；**Claude 通道的 astream 是伪流式**（整段一次
yield，无思考流）；英文思考碎片对中文用户观感一般。

### 4.6 消息投票 / 管理台满意度——2026-10-24 转真实

**技术原理**：模板自带的点赞/点踩原是空壳（PATCH 恒 200 不落库）。现改为
threads 库 `message_votes` 表（chat_id+message_id 主键），8800 `GET/PATCH /api/vote`
真落库（同票再点=取消、换票=覆盖，访客放行）；前端 message-actions 改调 8800 并带
`x-bank-token` 头；管理台 `GET /api/votes` 跨库只读（`_rec_rows` 模式），首页新增
「用户满意度」卡片（总数/赞/踩/百分比+最近 50 条明细）。

**产品策略**：线上反馈闭环——用户侧点按零学习成本，运营侧管理台一眼看满意度。

**优缺点**：链路全真、8 例测试覆盖；缺点：无按用户/时间的维度分析，明细只有
消息 id 不带内容摘要（刻意——消息本体在检查点库，避免跨库 join 复杂化）。

### 4.7 确定性反问选项卡——2026-10-23

**技术原理**：缺槽反问节点工厂（`_make_clarify_node`）支持 options 回调——枚举型
反问（如订阅缺 action）附带可点选项，载荷 `data-ask-slot {question, missing, options}`，
前端渲染按钮点击即以该文本回话（走正常 resume 通道，零新增协议）。

**产品策略**：把"你必须打字回答"变成"点一下就达"，枚举槽位的交互成本趋近于零。

**优缺点**：实现克制（复用 interrupt 语义）、覆盖 t/sb/c/s 四管线；缺点：选项由
代码写死（每业务一份 `_xxx_options`），新增业务要手补；自由输入型反问无选项。

### 4.8 手机扫码登录——2026-10-20

**技术原理**：电脑端登录后点「手机端登录」→ 8800 发一次性票据（进程内存，TTL 120s）
→ 二维码内容为 `http://<局域网IP>:3000/qr-login?ticket=…`（本机 /api/lan-info 探测
局域网 IP，全程不出网）→ 手机扫码免密登录同一账号。防火墙预置
「AI Banking Mobile Demo 3000/8800」入站规则。

**产品策略**：演示"同一账号多端"的银行级体验，票据一次性+短时效保安全。

**优缺点**：零外部依赖（不依赖二维码云服务）；强依赖局域网可达性——设备隔离的
校园网（eduroam 实测）直接失败，演示前用手机热点最稳。

### 4.9 测试与质量体系

**技术原理**：pytest 392 例全绿（~60s）；测试通过进程内 MCP 工具替身
（`tests/_mcp_inprocess.py`）消除子进程冷启动（1479s→60s 的提速来源）；想验证真实
stdio 链路设 `BANK_TESTS_STDIO=1`。契约守卫 `tests/test_contract.py` 冻结 SSE data-*
部件集合（前后端必须一致，卡载荷加字段要三处同步——守卫会拦）。前端另有 6 个
`webui/e2e-*.mjs` 场景脚本（转账/收款人/扫码登录/模型设置/移动端），截图输出
`gui-test-*/`（已 gitignore）。LLM 真评：`scripts/eval_agent.py`（25 剧本，需真 Key）。

**优缺点**：替身层对齐了 unwrap 契约/异常文本/用户隔离语义，速度与覆盖兼得；
缺点：e2e 依赖真浏览器手工跑（未进 CI），前端回归靠人。
