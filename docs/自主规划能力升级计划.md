# 自主规划能力升级计划

> 目的：回答"什么样的智能体才算会自主规划"，并给出本项目从"固定业务子图"升级到
> "可验收的自主规划智能体"的实施路线。  
> 适用赛题：2026 深圳国际金融科技大赛 · AI Banking Agent 赛道。  
> 本文是计划，不代表当前已全部实现；当前产品事实以
> [产品功能说明](产品功能说明.md) 为准。

---

## 一、先定义：什么叫"自主规划"

"自主规划"不是"多调几个工具"，也不是"LLM 多写几段话"。一个智能体要被称为会自主规划，
至少要同时满足下面 8 条：

1. **目标理解**：用户给的是目标（"把老婆生日安排好，别动房租"），不是一步一步的操作指令；
   智能体能识别目标、约束、偏好和缺失信息。
2. **计划生成**：能把目标拆成有依赖关系的步骤，明确每步用什么能力、输入输出、
   成功条件和风险等级，而不是走一条写死的流程。
3. **能力选择**：面对同一目标，能根据当前账户、预算、事件、订阅、风险等级选择不同能力
   或不同顺序；不是所有请求都命中同一个子图。
4. **执行与观测**：按依赖顺序执行，读操作可并行，写操作串行；每一步都记录结果，
   拿结果和预期对比。
5. **失败后重规划**：余额不足、工具失败、风控拒绝、信息冲突时，能定位受影响步骤，
   只修复子计划或提出替代方案，而不是整段重来或直接报错。
6. **约束满足**：计划必须满足用户约束（预算、时间、不能动房租）和银行约束
   （限额、风险等级、支付密码、幂等）；违反约束的计划不能执行。
7. **人在回路**：计划可查看、可修改；动钱/敏感操作必须人工确认；重规划后要展示差异。
   银行场景里"不能全自动扣款"是正确设计，不是不自主。
8. **可解释、可审计、可复现**：能说清"为什么这样排、哪步失败了、改了什么"；
   计划、步骤、工具调用、审批和结果都能留痕，失败可回放。

一句话：**自主规划 = 目标 → 可检查的计划 → 有边界的执行 → 观测 → 重规划 → 可审计收尾**。
只会按固定顺序调用工具，叫"工作流自动化"；只会生成计划但不执行/不修正，叫"计划文本生成"。

## 二、成熟度分级：本项目应该做到哪一级

| 等级 | 名称 | 特征 | 本项目现状 |
|---|---|---|---|
| L0 | 固定工作流 | 意图路由到固定子图，步骤写死；LLM 只做抽取/播报 | **当前大部分场景在此** |
| L1 | 生成式计划 | LLM 生成计划文本/步骤，但执行仍走固定路径 | 局部有（联动计划），未形成通用计划器 |
| L2 | 闭环规划 | 计划可执行、可观测、失败可局部重规划；约束与人工闸门强制 | **建议作为比赛目标** |
| L3 | 长程主动规划 | 主动发现目标（账单/事件/订阅），跨天跨场景，有长期记忆和优先级 | 有事件/提醒雏形，未闭环 |
| L4 | 开放式多智能体 | 任意目标、动态创建工具/子智能体、长期学习 | 不建议在比赛周期追求 |

比赛答辩时不要笼统说"我们自主规划"，而应说：

> "我们当前是 L2 闭环规划：LLM 负责把目标拆成受约束的计划，执行器按依赖执行并观测，
> 失败时只重规划受影响部分；动钱步骤始终保留人工确认和支付密码闸门。"

L2 已经足够打动评委，且与银行安全边界相容。

## 三、现状对照：我们已有什么、缺什么

### 3.1 已有的"规划素材"

- 10 个路由意图与多套业务子图：转账、AA、账单、理财、卡片、订阅、联动、联系人等。
- 多步执行能力：建单→确认→扣款；风险测评→推荐→申购；事件→预算锁定→提醒→逐项购买。
- 局部反思/澄清：缺槽反问、同名联系人消歧、闸门犹豫封顶、工具错误播报。
- 约束执行：限额、风险等级、支付密码、幂等键、审计日志。
- 可观测基础：`bank_calls`、`notice`、SSE 卡片、审计/变更/资金三套记录。
- 联动计划数据结构：预算、动作、提前天数、提醒任务、逐项执行状态。

### 3.2 关键缺口

| 缺口 | 现状 | 为什么不算自主规划 |
|---|---|---|
| 没有显式 Plan 对象 | 每轮由路由选一个子图，步骤在代码里 | 无法展示"计划"，也无法局部修改/重放 |
| 没有通用 Planner | 计划由固定节点序列决定 | 同一目标换个约束，路径不会变 |
| 不会跨域组合 | 路由只选一个意图 | "先砍订阅再准备生日"这类目标做不了 |
| 没有工具/技能目录 | LLM 看不到工具元数据 | 不能根据风险/前置条件选择能力 |
| 没有重规划闭环 | 工具失败多是报错收尾 | 余额不足/风控拒绝后不会给替代方案 |
| 没有计划级记忆 | 只有会话消息和槽位 | 不能复用上次计划、预算偏好、失败经验 |
| 没有主动发现 | 提醒靠打开网页/点按钮 | 不会自己发现"生日快到了/订阅涨价了" |
| 没有规划评估 | 评估的是单场景剧本 | 无法证明"规划质量"而非"流程能跑" |

结论：**当前是 L0/L1 之间的"固定子图 + 局部计划"，还不是可验收的自主规划智能体。**

## 四、目标架构：Planner + Executor + Reflector + Guard + Memory

不推翻现有银行能力层和子图；把它们降级为"可被计划调用的技能（Skills）"。

```
用户目标
  │
  ▼
[Goal Parser] 目标/约束/偏好/缺失信息
  │
  ▼
[Planner] 生成 Plan(JSON)：步骤、依赖、风险、闸门、成功条件、fallback
  │         ↖ 技能目录 + 用户记忆 + 账户/事件/订阅快照
  ▼
[Plan Guard] 静态校验：预算/限额/风险/依赖/步数/时间/禁止自动确认
  │
  ▼
[Plan Card / 人工审批] 计划可见、可改；高风险计划先确认
  │
  ▼
[Executor] 拓扑执行：读并行、写串行；幂等；逐步记录
  │
  ├─ 成功 → [Reflector] 对照成功条件 → 下一步/收尾
  ├─ 缺信息 → 追问用户（计划保留，不丢已完成步骤）
  ├─ 可恢复失败 → 局部重规划（只改受影响子图）
  └─ 风控/约束冲突 → 停止并给替代方案，绝不绕过
  │
  ▼
[Plan Trace / Audit] 计划版本、步骤状态、工具调用、审批、结果
```

### 4.1 Plan 对象（必须显式、可持久化）

```json
{
  "plan_id": "plan_xxx",
  "goal": "准备老婆生日，预算1000，不动房租",
  "constraints": [
    {"type": "budget", "value": 1000},
    {"type": "do_not_touch", "value": "房租"}
  ],
  "assumptions": ["生日事件已存在", "活期余额充足"],
  "steps": [
    {
      "id": "s1",
      "skill": "get_financial_snapshot",
      "args": {},
      "depends_on": [],
      "risk": "READ",
      "gate": null,
      "success": "返回余额/近期支出/订阅",
      "on_fail": "replan"
    },
    {
      "id": "s2",
      "skill": "lock_budget",
      "args": {"amount_yuan": "1000", "memo": "生日预留"},
      "depends_on": ["s1"],
      "risk": "HIGH",
      "gate": "confirm_transfer",
      "success": "锁定单 executed",
      "on_fail": "replan"
    },
    {
      "id": "s3",
      "skill": "schedule_gift_actions",
      "args": {"days_before": 2, "what": ["鲜花", "蛋糕"]},
      "depends_on": ["s2"],
      "risk": "LOW",
      "gate": null,
      "success": "提醒任务 pending"
    }
  ],
  "success_criteria": ["预算已锁定", "生日前2天提醒已排程", "未动房租"],
  "fallback": ["余额不足→先分析订阅可省金额", "预算冲突→降低礼物预算"]
}
```

约束：
- 步骤只能引用**技能目录**里的 skill，不能直接引用 `confirm_transfer_order` 等底层动钱工具。
- `gate` 是执行器强制的，不是 Planner 可选的；Planner 不给出合法 gate，执行器拒绝。
- 计划必须通过 JSON Schema 校验；解析失败→回到 Planner（最多 2 次）→仍失败则安全兜底。

### 4.2 技能目录（Skill Registry）

现有 MCP 工具太多且风险不一，Planner 不应直接面对 44 个原始工具。建立一层技能：

| 技能 | 内部工具 | 风险 | 典型用途 |
|---|---|---|---|
| `get_financial_snapshot` | get_accounts + get_transactions + list_subscriptions | READ | 给规划提供事实 |
| `analyze_spending` | category_summary/monthly_report/detect_anomalies | READ | 找可省空间 |
| `lock_budget` | create_transfer_order + confirm_transfer_order | HIGH | 生日预算锁定 |
| `prepare_birthday` | list_events + create_linkage_plan | MED | 生日计划 |
| `review_subscriptions` | detect_subscriptions + list_upcoming_precharges | READ | 续费/涨价 |
| `cancel_subscription` | s_gate + cancel_subscription | HIGH | 省钱执行 |
| `transfer_to_contact` | t_* 子图 | HIGH | 转账 |
| `adjust_card` | k_* 子图 | MED/HIGH | 卡片 |
| `invest_product` | w_* 子图 | HIGH | 理财 |

每个技能声明：描述、输入 schema、输出、风险、前置条件、是否幂等、是否必须人工闸门。
Planner 只看技能，不看底层工具；执行器负责把技能映射到现有子图/工具，并强制闸门。

### 4.3 执行器

- 按 `depends_on` 拓扑排序；同一层只读步骤可并行，写步骤串行。
- 每步执行前检查前置条件（余额、状态、归属、限额）；执行后校验成功条件。
- 所有写技能带幂等键：`plan_id + step_id`，重放不重复扣款。
- 最大步数（如 12）、最大重规划次数（如 3）、最大时长（如 120s），超限安全停止。
- 计划状态持久化：`pending_approval / running / waiting_user / replanning / done / failed / cancelled`。
- 服务重启后可恢复：已完成的步骤不重跑，未完成的从断点继续。

### 4.4 反思与重规划

只允许"局部修复"，不允许 Planner 每次推倒重来：

| 触发 | 处理 |
|---|---|
| 缺槽/歧义 | 保留已完成步骤，向用户追问；计划状态 `waiting_user` |
| 余额不足 | 检查可省订阅/降低礼物预算/改时间，给 2 个替代方案，由用户选 |
| 风控拒绝 | 解释触发的限额/风险规则；提出合法替代（改金额/先测评/换卡），不得绕过 |
| 工具超时/失败 | 只重试该步骤一次；仍失败则替换技能或跳过（仅只读可跳过） |
| 用户改约束 | 重算受影响子图，保留无关已完成步骤，展示 plan diff |
| 用户说"取消" | 取消计划；已建未确认的锁定单/提醒一并撤销；已执行的写操作不擅自回滚 |

重规划必须输出 `plan_version` 和差异（新增/删除/修改了哪些步骤），前端展示后再执行。

### 4.5 人机边界（银行场景的硬规则）

- Planner 可以规划动钱，但**不允许规划"自动确认"**；`confirm_transfer_order` 等确认动作只能由用户触发。
- 多步/高风险计划先展示 Plan Card，用户确认后再执行。
- 每个动钱步骤仍要支付密码；计划审批不能代替支付密码。
- 用户可编辑计划参数（预算、时间、礼物），编辑后必须重新过 Guard。
- 任何绕过 Guard 的执行路径视为安全缺陷，测试直接红。

### 4.6 记忆与主动发现

- 用户记忆：预算偏好、风险等级、常用收款人、重要事件、上次计划与失败原因。
- 事实快照：账户余额、本月支出、订阅清单、待确认单；规划前刷新，避免拿旧数据排计划。
- 主动触发：事件临近、订阅涨价、异常交易、余额不足时，生成"建议计划"推送到会话/IM；
  用户确认后才进入执行。
- 记忆只做建议，不能替代当前事实校验；执行前仍要读实时余额/限额。

## 五、怎样才算验收通过（Definition of Done）

### 5.1 能力验收清单

一个目标要算"自主规划通过"，必须同时满足：

1. 目标里有至少 2 个约束（预算/时间/不能动某笔钱/风险等级）。
2. 计划是动态生成的，能看到步骤、依赖、风险、成功条件；不是固定子图回放。
3. 换一个约束（预算 600 vs 1500），计划会变（步骤/金额/顺序至少一处不同）。
4. 至少一次可恢复失败触发局部重规划（余额不足/风控拒绝/工具失败）。
5. 重规划后已完成步骤不重跑，未受影响步骤不改变，展示 diff。
6. 所有动钱步骤都经过人工闸门 + 支付密码；无任何自动确认。
7. 全程有 plan trace：计划版本、步骤状态、工具调用、审批、结果。
8. 计划可取消、可恢复；服务重启后未完成计划能继续。
9. 约束违反率为 0；越权/绕过闸门尝试为 0。
10. 能解释"为什么这样排、为什么改"。

### 5.2 建议的评估场景（新增 5 个多步剧本）

| 剧本 | 目标 | 关键约束/注入 | 期望 |
|---|---|---|---|
| P1 生日预算 | "准备老婆生日，预算1000，别动房租" | 事件存在；余额可不足 | 计划→锁预算→排提醒；不足时先分析订阅/降礼物预算 |
| P2 省钱 | "这个月超支了，帮我把订阅砍出200元" | 订阅涨价；取消需支付密码 | 账单分析→订阅预审→逐项取消闸门；不误伤其他订阅 |
| P3 工资分配 | "工资到账5000，房租3000、理财1000、零花1000" | 日限额/风险等级 | 多步转账+理财；限额拒绝时重排，不超限 |
| P4 出差 | "下周出差，信用卡额度调到1万，还款日提醒我" | 卡片锁定/限额规则 | 卡片闸门+提醒；非活跃卡先解锁再调额 |
| P5 异常+行动 | "最近有异常扣款吗？有的话帮我处理" | 异常规则命中；订阅误扣 | 异常报告→定位商户→取消/挂失/提醒，按风险分流 |

### 5.3 指标

- 任务成功率（多步目标完成）
- 约束满足率（预算/时间/不动某笔钱）
- 计划有效率（Guard 通过率、Schema 合法率）
- 重规划成功率与平均重规划次数
- 人工干预次数（越低越自主，但动钱闸门不计入"失败"）
- 不安全尝试数（必须 0）
- 端到端时延、模型 token 成本
- 可解释性（计划/差异/失败原因是否完整）

建议门槛：5 个剧本成功率 ≥ 80%，约束满足率 100%，不安全尝试 0，
至少 2 个剧本在注入失败后完成局部重规划。

## 六、实施路线（建议 3 周，比赛版可压缩到 7-9 天）

### 第 1 周：显式 Plan + Planner（只读）

- 定义 Plan JSON Schema、技能目录（先 6 个技能）。
- 新增 `planner` 节点：目标→Plan；`plan_guard` 静态校验；`plan_card` 前端展示。
- 先只允许 READ 技能：财务快照、账单分析、订阅清单、事件查询。
- 验收：P1/P2 能生成并展示计划，不执行写操作；换约束计划会变。

### 第 2 周：Executor + 闸门 + 持久化

- `plan_executor` 按拓扑执行；接现有子图/工具；写步骤强制 gate。
- `plans` / `plan_steps` 表，状态机与断点恢复；计划取消。
- 前端 Plan Card：步骤状态、风险标识、编辑预算/时间、取消。
- 验收：P1 生日计划完整执行（锁预算+排提醒）；P3 工资分配在限额内完成。

### 第 3 周：Reflector + 重规划 + 评估

- 失败分类与局部重规划；plan diff；最多 3 次。
- 注入余额不足、工具 500、风控拒绝、同名联系人；验证不越权。
- 新增 5 个规划剧本到 `scripts/eval_agent.py`，统计指标；答辩材料更新。
- 验收：5 个剧本 ≥ 80%，约束 100%，不安全 0，2 个重规划通过。

### 比赛最小版（7-9 天）

如果时间紧，只做 **2 个跨域剧本 + 1 条重规划路径**：

1. 生日预算（P1）：快照→锁预算→排提醒；余额不足→先分析订阅/降礼物预算。
2. 省钱（P2）：账单→订阅预审→取消（支付密码）→复算节省金额。
3. 只做"余额不足"和"风控拒绝"两种重规划；其余失败安全停止。
4. 计划只支持 5-6 个技能，不追求通用工具规划。
5. 计划卡 + trace + 评估报告齐全，就能支撑"L2 闭环规划"的答辩。

## 七、不要做的反模式

- **让 LLM 直接调用确认/扣款工具**：绕过闸门，零容忍。
- **把"多轮 LLM 调用"当规划**：评委换一个没见过的目标就会露馅。
- **每次失败整段重跑**：已完成步骤重放会重复扣款/重复建单。
- **没有约束和成功条件的计划**：只是步骤列表，无法验收。
- **无限重规划/无限步数**：必须设上限，超限安全停止。
- **计划只在后端，用户看不见**：黑盒计划不能算自主，至少要可查看/可修改。
- **把主动推送做成"打开网页才提醒"**：这不叫主动发现；需要后台调度/IM 渠道。
- **为了显得自主而取消支付密码**：银行场景里这是减分项，不是加分项。

## 八、答辩演示脚本（3 分钟）

1. **给一个没排练过的多约束目标**：
   "下周三我老婆生日，预算 1000，别动房租；如果这个月钱不够，先看看哪些订阅能砍。"
2. 智能体先拉快照，展示 **Plan Card**：分析支出→锁预算→排礼物提醒；
   标注哪些步骤只读、哪些要支付密码、成功条件是什么。
3. 注入余额不足（或把预算改成 1500）：智能体只改受影响子图，
   给出"砍订阅/降礼物预算"两个替代，展示 plan diff；用户选一个。
4. 执行只读步骤；到动钱步骤弹出支付密码闸门；用户确认后继续。
5. 打开 **Plan Trace**：每步状态、工具调用、审批、结果、审计；
   指出"已完成步骤没有重跑，违反约束的计划被执行器拒绝"。
6. 收尾一句话：
   "我们的自主规划是 L2 闭环：目标→计划→执行→观测→局部重规划；
   动钱保留人工确认，这是银行场景的边界，不是能力缺失。"

## 九、结论

要被称为"自主规划的智能体"，本项目必须从"意图→固定子图"升级为
"目标→显式计划→受约束执行→观测→局部重规划→可审计"。

比赛周期内不需要追求 L4 开放式规划；做到 **L2 闭环规划 + 银行级安全边界**，
并用 2-3 个跨域剧本、1-2 条失败重规划路径、Plan Card/Trace 和量化评估证明，
就足以支撑"自主规划"这一要点。当前最优先的三件事是：

1. 把 Plan 变成显式、可持久化、可展示的对象；
2. 建技能目录，让 Planner 基于能力和风险选择，而不是直接碰底层工具；
3. 做局部重规划闭环，并用注入失败证明它真的会改计划、且不会越权。

## 十、最小成本参赛演示方案（2-3 天，L2-lite）

如果目标不是"做完整 L2"，而是**比赛现场用最低成本讲清楚自主规划**，建议只做一个场景：
**生日预算规划**。复用现有事件、`suggest_linkage`、联动计划、支付密码闸门，
**零新表、零新调度、零新支付逻辑**。

### 10.1 只加三个东西

1. **一个规划前置节点（后端）**
   - 触发：现有"帮我准备生日"建议，或用户说"帮我规划老婆生日，预算1000"。
   - 步骤：
     - `list_events` 找最近的生日事件；找不到才追问日期。
     - `get_accounts` / `get_transactions` 看可用余额和近期支出。
     - `suggest_linkage(event_id)` 取现成的计划草稿（预留资金 + 提前2天提醒）。
     - 组装 `plan`：目标、约束（预算/不动固定支出）、步骤、每步风险/闸门、
       成功条件、数据依据；**不执行任何写操作**。
   - 数据分支（这就是"自主"的最小证明）：
     - 预算 ≤ 可用余额 - 安全垫 → 计划"锁定1000 + 排礼物提醒"。
     - 预算 > 可用余额 - 安全垫 → 计划自动下调预算，并写明
       "可用余额不足，预算从1000调整为800；如需保留1000，需先取消订阅/降低礼物"。
   - 计划作为 `confirm_plan` 闸门发出 `data-plan` 卡；`pending_payload` 已有机制会持久化，
     刷新/换设备可以恢复（不用建新表）。

2. **一张 PlanCard（前端）**
   - 展示：目标、约束、数据依据、步骤列表（只读/动钱/提醒）、风险标识、
     预计成功结果、预算调整原因。
   - 按钮：`执行计划`（发"确认计划"恢复图）、`调整预算`（改数字后重新生成计划）、`取消`。
   - 样式复用现有金色闸门卡的视觉语言，放在 `bank-parts.tsx`，新增 `data-plan` 映射。

3. **一个 e2e + 两个 pytest**
   - pytest：计划生成（余额充足/不足两种预算）、确认后进入既有联动支付密码闸门、
     未确认前零写操作。
   - e2e：说"帮我准备生日"→ PlanCard 出现→改预算→计划变化→执行→支付密码→
     锁定单/提醒任务落库；截图留证。

### 10.2 执行路径（复用现有能力，不写新执行器）

```
用户目标
  → p_plan_snapshot（只读：事件/账户/订阅）
  → p_plan_build（生成 Plan，按余额分支）
  → confirm_plan 闸门（PlanCard，无支付密码）
  → 用户"确认计划"
  → 复用 l_plan：create_linkage_plan（建锁定单 + 排提醒）
  → 复用 l_gate：confirm_linkage（支付密码）
  → 完成；审计/流水照旧
```

- PlanCard 的"执行计划"只负责把用户意图交给现有联动流程；**扣款仍然要过原有支付密码闸门**。
- 不实现通用工具选择、不实现多计划并行、不实现计划持久化表；Plan 存在图状态/闸门载荷里。
- 如果预算不足分支只做"自动下调预算"，不自动取消订阅（取消订阅要另一道支付密码闸门，
  成本高且容易在现场多点一次）。文案里给用户"取消订阅"的建议，让用户自己去订阅场景操作即可。

### 10.3 现场 90 秒演示脚本

1. 说："帮我准备老婆生日，预算 1000"。
2. 出现 PlanCard：读取到"林悦的生日（4天后）"、活期余额、本月支出；
   计划三步：锁定预算 → 生日前2天鲜花/蛋糕提醒 → 确认。
3. 点"调整预算"改成 3000：PlanCard 立即变成"余额不足，预算下调到 X；
   如要保留 3000，建议先取消一项订阅"，**计划步骤/金额发生变化**。
4. 改回 1000，点"执行计划"；进入既有支付密码闸门，输入 888888；
   锁定单执行、提醒任务落库。
5. 打开凭证/审计，说明："计划是动态的；动钱仍有支付密码；没有确认前零扣款"。
6. 诚实收尾："这是 L2-lite：单场景闭环规划，通用 Planner 是后续 3 周计划。"

### 10.4 这个方案能证明什么、不能证明什么

**能证明**
- 从目标/约束生成可检查计划，而不是直接走固定子图；
- 计划会读取实时余额并据此调整（数据驱动，不是纯模板）；
- 计划可编辑、可确认、可取消，刷新可恢复；
- 动钱仍受支付密码闸门保护，零越权。

**不能证明（答辩要主动说明）**
- 不是通用 Planner：只覆盖生日预算一个场景；
- 不做工具级动态选择/多计划并行/长期记忆；
- 不做执行失败后的多轮重规划（只有预算分支这一次重规划）；
- 不是 L2 全量，更不是 L3/L4。

### 10.5 工期与降级方案

| 版本 | 工期（1人） | 内容 | 风险 |
|---|---|---|---|
| 最小演示版（推荐） | 2-3 天 | 上述 1+2+3，含预算分支/e2e/截图 | 低；只碰联动链路 |
| 1 天降级版 | 1 天 | 只加 PlanCard，不做预算分支/执行接入，计划为静态三步 | 中；评委可能认为是"计划文本" |
| 完整 L2 | 2-3 周 | 通用 Planner/技能目录/局部重规划/5 剧本 | 高；不建议临时赶 |

**推荐选择 2-3 天最小演示版**：它的每一分成本都花在评委看得见的地方，
且不会破坏现有资金安全链。1 天降级版只能作为时间实在不够的兜底，
不要把它包装成"自主规划已完成"。

### 10.6 演示前检查清单

- 种子事件"林悦的生日"在 3-7 天内；否则现场用 `add_event` 或演示快进。
- 活期余额足够走"预算1000"分支；再准备一个低余额/高预算触发下调分支。
- PlanCard 的"执行计划"只恢复联动流程，支付密码闸门必须仍然出现。
- 确认未执行前 `transfer_orders` 没有新增锁定单、`scheduled_tasks` 没有新增提醒。
- 准备一张 PlanCard 截图和一张 plan trace/审计截图，防止现场模型/网络抖动。
