# 协作与接口契约（多人并行开发母版）

> 冻结基线:`aed2407`(2026-10-09) ｜ 适用:两人及以上并行开发本项目
> **一句话原则**:两个人同时改一套代码,唯一的交集是接口;接口不冻结,"各自开发再合并调试"就会变成人肉解冲突。

---

## 一、为什么不采用"各发一份项目文件,各写几个模块,最后合起来调"

这个思路的动机是对的(并行能快),但具体做法在本项目上会踩三个坑:

| 想法 | 本项目实况 | 后果 |
|------|-----------|------|
| "发我项目文件" | 已有私有远端 `git@github.com:legendofgithub/AI-banking.git`,SSH:443 通道可用 | 手工传文件 = 两份非正规分叉,最后要人肉拼 diff——**正是想省掉的那一步** |
| "做一个主界面母版" | UI 壳早已建好(webui + 银行卡片组件);真正的大文件是 `agent/graph.py`(**2533 行,九个场景全在一个文件**) | 母版做在 UI 上,等于没防住真正的冲突区 |
| "分几个模块,最后合并调试" | `agent/graph.py` 的建图段(节点注册 + 连边)是**所有人必改的公共区** | 冲突堆积到项目末期才爆发,离交付最近时最痛 |

**正确做法**:按层切(不是按场景切)+ 冻结接口契约 + 每天 rebase + 契约测试自动守。
分工建议与本项目研发计划一致(见 [AI-Banking-Agent-产品研发计划.md](AI-Banking-Agent-产品研发计划.md) §6)。

---

## 二、分工:按层切,不按场景切

**为什么不能按场景切**:六个场景并不是六个独立模块,而是同一套代码里的九个前缀
(`t_`/`sb_`/`ss_`/`c_`/`l_`/`b_`/`w_`/`k_`/`s_`),全部挤在 `agent/graph.py` 一个文件里。
"你三个场景、我三个场景"= 两个人同时改同一个文件的不同位置,Git 每次都要手工解冲突。

**按层切则天然低冲突**——两层的文件几乎不重叠:

| 角色 | 独占目录 | 职责 | 不碰 |
|------|---------|------|------|
| **A · 后端 / Agent 编排** | `bank_core/**`、`agent/**`、`tests/**`、`scripts/**` | 42 个 MCP 工具、账本/分析/理财/事件/联动、LangGraph 编排、8800/8788/8789 三个 API | `webui/**`、`admin_console/**`、`demo/**` |
| **B · 前端 / 交互** | `webui/**`、`admin_console/**`、`demo/**` | 聊天前端、银行卡片组件、generative UI、管理台页面 | `bank_core/**`、`agent/**` |

**两层之间唯一的耦合点**,就是下面第三节的契约。它是这份文档存在的全部理由。

## 三、冻结的接口契约(核心)

### 3.1 唯一接缝:四段串联

```
agent/graph.py          interrupt({"type": "confirm_transfer", ...})     闸门载荷
      ↓                 agent/api.py::_interrupt_frames 映射
agent/api.py            {"type": "data-transfer-confirmation", "data":…}  SSE 部件
      ↓                 UIMessageStream 线协议(SSE)
webui/…/bank-parts.tsx  type === "data-transfer-confirmation"            前端渲染
```

**关键风险**:任何一层单方面增删类型,另外两层都不会报错——**只会"卡片静默不显示"**。
这类故障在演示现场最难查,所以由自动测试兜底(见第四节)。

### 3.2 完整契约表(11 个闸门 → 13 个 SSE 部件)

首次冻结时实测 **后端 13 种 / 前端 13 种,零漂移**。改动此表必须三处同步。

| # | 场景 | 闸门类型(`graph.py` 抛出) | SSE 部件 | `data` 载荷字段 | 前端组件 |
|---|------|--------------------------|---------|----------------|---------|
| 1 | 转账 `t_` | `confirm_transfer` | `data-transfer-confirmation` | 转账卡(见 `_transfer_card`) | `BankDataPart` |
| 2 | AA 收款 `sb_` | `confirm_split` | `data-split-confirmation` | 账单视图 + `pay_required` | 同上 |
| 3 | AA 结算 `ss_` | `confirm_settle` | `data-settle-confirmation` | 结算视图 + `pay_required` | 同上 |
| 4 | 联系人 `c_` | `pick_contact` | `data-contact-choices` | `candidates[]` | 同上 |
| 5 | 联系人 `c_` | `confirm_contact` | `data-contact-confirmation` | 草稿 + `pay_required` | 同上 |
| 6 | 联动 `l_` | `confirm_linkage` | `data-linkage-plan` | 计划视图 + `pay_required` | 同上 |
| 7 | 联动 `l_` | `confirm_linkage_action` | `data-linkage-action` | 动作视图 + `pay_required` | 同上 |
| 8 | 理财 `w_` | `confirm_wealth` | `data-wealth-confirmation` | `{kind, order, pay_required}`,`kind=subscribe\|redeem` | 同上 |
| 9 | 卡片 `k_` | `confirm_card` | `data-card-confirmation` | `{kind, card, pay_required}`,`kind=apply\|limits\|status` | 同上 |
| 10 | 订阅 `s_` | `confirm_sub_cancel` | `data-subscription-cancel` | 订阅视图 + `pay_required` | 同上 |
| 11 | 全场景 | `ask_slot`(缺槽反问) | `data-ask-slot` | `missing[]` | 同上 |
| — | 订阅 `s_` | *(无闸门,`s_list` 节点直接下发)* | `data-subscription-list` | `update["sub_view"]` | 同上 |
| — | 全场景 | *(本轮停在闸门时收尾下发)* | `data-gate-pending` | `{gate_type, question}` | 同上 |

> `pay_required` 语义:为真时前端渲染支付密码输入框。它可能是布尔值,也可能是
> `lambda state: ...`(如卡片闸门仅"改限额/改状态"需要),由 `graph.py` 求值后
> 在载荷里给出布尔结果。

### 3.3 SSE 线协议词表(不可自创)

线格式 = SSE,每帧 `data: {json}\n\n`;响应头必须带 `x-vercel-ai-ui-message-stream: v1`。
词表取自 Vercel AI SDK 5 的 `UIMessageChunk`(逐条核对过源码,详见 `agent/api.py` 头部注释):

```
{"type": "start"}                                    流开始
{"type": "text-start",  "id": "…"}                   文本块开始
{"type": "text-delta",  "id": "…", "delta": "…"}     文本增量(是 delta,不是 textDelta)
{"type": "text-end",    "id": "…"}                   文本块结束
{"type": "data-<name>", "data": {...}}               自定义部件(必须 data- 前缀)
{"type": "error",       "errorText": "…"}            错误(字段名就是 errorText)
{"type": "finish",      "finishReason": "…"}         结束
```

**踩坑**:写错字段名(如 `textDelta`/`errorMessage`)会让前端 `useChat` 整帧丢弃——
流看起来"卡住",但服务端日志一切正常。

### 3.4 会话驱动约定

- 请求只取**最后一条 user 消息**作为新输入;完整历史由 checkpointer 按 `thread_id` 保持。
- 同一 thread 若停在 interrupt,下一条消息自动作为 `Command(resume=文本)` 恢复——
  前端只需照常把用户回复发上来,**不必区分"新指令"还是"闸门答复"**。
- 播报白名单 `ANNOUNCE_NODES`(`agent/api.py`)决定哪些节点的文本会播报给用户;
  节点改名而白名单未同步 → 该场景**静默不再播报任何文本**。

## 四、契约守卫测试(自动红灯)

`tests/test_contract.py` 把这四段接缝变成 pytest 断言。**纯静态源码解析,零依赖,0.04 秒跑完。**

| 测试 | 拦住什么 |
|------|---------|
| `test_every_gate_type_is_mapped_by_api` | 图新增闸门但 api 没映射 → **卡片不渲染** |
| `test_api_has_no_orphan_gate_mapping` | 图改名而 api 留旧分支 / 死代码 |
| `test_data_part_types_match_between_backend_and_frontend` | **后端多发** → 前端静默不渲染;**前端多认** → 卡片永不出现 |
| `test_sse_frames_stay_within_wire_vocabulary` | 帧类型写错(如 `textDelta`)→ 前端整帧丢弃 |
| `test_announce_nodes_all_exist_in_graph` | 节点改名而播报白名单未同步 → **静默不播报** |

**有效性已验证**:故意在前端注入 `data-fake-card` 后,该测试精准失败并指出
"前端处理但后端从不发出:['data-fake-card']";还原后全绿。它不是摆设。

> 维护提示:该文件用源码静态解析(因为建图需要 MCP 工具与 LLM)。若将来把
> `agent/graph.py` 重构为包,需同步调整其中 `RE_NODE_REGISTRY` 相关的解析逻辑。

## 五、不许破坏的不变量(资金安全铁律)

分头开发最容易踩坏的不是接口,是**业务不变量**。以下五条是 `bank_core` 现有强制设计,
任何人不得为"跑通演示"而绕过:

1. **动钱两步走**:建单 → 确认,才真正扣款。
2. **幂等防重放**:同一轮重复提交不得重复扣款。
3. **理财风险闸门**:超过用户风险等级(C 级以上)一律拒购。
4. **支付密码 4 次锁定**:连错锁定转账功能,**仅管理员可解**。
5. **全量审计日志**:每一笔资金动作都有审计记录。

> 合并前请务必跑全量测试并**手工走一遍动钱链路**——单元测试拦不住前端表单问题
> (见 `AGENTS.md` 铁律 4)。

## 六、分支与提交规范

### 6.1 分支命名

```
main                       仅接受通过全量测试的合并
feat/be-<主题>             角色 A:后端/Agent,如 feat/be-subscription-detect
feat/fe-<主题>             角色 B:前端,如 feat/fe-card-limits-ui
fix/<主题>                 缺陷修复
```

按层切的好处:分支名带 `be-`/`fe-` 前缀后,一眼能看出**这次改动是否触及契约**。

### 6.2 每日循环(两人都照做)

```bash
# 开工:先同步,再干活(rebase 而非 merge,保持线性历史)
git switch main && git pull --rebase
git switch feat/fe-xxx && git rebase main

# 干活:小步走 —— 一个功能 → 跑测试 → 一个语义化 commit

# 收工:推分支,开 PR(不要直接推 main)
git push -u origin feat/fe-xxx
```

### 6.3 合并前必做(四条,缺一不可)

```bash
# 1. 契约没被单方面改动
.venv/Scripts/python.exe -m pytest tests/test_contract.py -q

# 2. 全量回归(当前 133 个,全绿才交付)
.venv/Scripts/python.exe -m pytest tests -q

# 3. 前端改了就重新 build 并实跑(不是跑测试就算)
cd webui && node e2e-check.mjs

# 4. 动了钱链路 → 浏览器里实际走一遍转账全流程
```

### 6.4 冲突高发区与规避

| 文件 | 冲突程度 | 规避 |
|------|---------|------|
| `agent/graph.py` 建图段(约 2701–2843 行) | 🔴 最高 | 归角色 A 独占;若必须两人改,**当天小步提交**,不要攒 |
| `webui/components/chat/bank-parts.tsx` | 🟠 高 | 归角色 B 独占;新增卡片类型务必同步契约表 |
| `bank_core/mcp_server.py`(工具注册区) | 🟡 中 | 追加式修改,冲突可自动合并 |
| `AGENTS.md` / 本文档 | 🟢 低 | 谁改谁在 commit message 里说明 |

### 7.2 本地环境(必须自建,仓库不含环境)

⚠️ **`.venv/`、`webui/node_modules/`、`data/` 全部不入库**——直接 clone 下来是**跑不起来**的。
(仓库仅 271 个跟踪文件。)队友需按顺序执行:

```bash
# ① Python 侧 —— 必须用 Python 3.12(见下方说明)
py -3.12 -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt

# ② 生成 12 个月演示种子数据(不入库,必须自己播种)
.venv/Scripts/python.exe -m bank_core.seed

# ③ 前端(必须加镜像源)
cd webui && pnpm install --registry=https://registry.npmmirror.com
```

**三个已实测的坑,照做就不会中招:**

1. **必须用 `py -3.12`,不要用裸 `python -m venv`。**
   本机 `py -0p` 的默认版本是 **3.14**,而项目依赖装在 3.12 上
   (现有 `.venv/pyvenv.cfg` = Python 3.12.9)。用错版本建出来的环境跑不起来。
   先确认:`py -0p` 应能看到 3.12;没有就装一个。

2. **`requirements*.txt` 必须保持纯 ASCII。**
   2026-10-09 实测:文件里含中文注释时,中文 Windows 下 pip 会用 GBK 解码而抛
   `UnicodeDecodeError`,**一个包都装不上**。已改为英文注释;以后别往这两个文件里写中文。

3. **装完确认依赖齐全**(应约 111 个包):
   ```bash
   .venv/Scripts/python.exe -m pip list --format=freeze | wc -l
   ```
   若要**逐字节复现**当前环境,改用精确快照:
   `.venv/Scripts/python.exe -m pip install -r requirements.lock.txt`
   (`requirements.txt` 是区间约束,会装到更新的小版本;`lock` 是精确版本。)

### 7.3 密钥与数据(注意保密)

- `webui/.env.local` **不入库**,需通过私下渠道传给队友。**绝不要为了图省事提交它。**
  把它复制成 `webui/.env.local` 即可;需要哪些键以 **`webui/.env.example` 为准**
  (该文件已按实测校准,2026-10-09)。真正的必填项只有四类:

  | 键 | 说明 |
  |----|------|
  | `AUTH_SECRET` | NextAuth 会话签名密钥,随便一串 32 字节随机串 |
  | `AUTH_URL` | `http://127.0.0.1:3000` |
  | `ZAI_BASE_URL` / `ZAI_API_KEY` / `ZAI_MODEL` | LLM 配置,**三个必须一起改** |
  | `NEXT_PUBLIC_AGENT_API_PORT` | 选填,不写默认 `8800` |

- ⚠️ **模板残留键不用配**:`POSTGRES_URL` / `REDIS_URL` / `BLOB_READ_WRITE_TOKEN`
  在本项目中从不被读取(银行账号体系走 8800 自有实现,浏览器用 localStorage 存
  `bank-token`),`webui/.env.example` 里已移除,别浪费时间搭 Postgres。
- ⚠️ 代码读的是 `NEXT_PUBLIC_AGENT_API_**PORT**`,不是 `..._URL`——写成 URL 不生效。
- 演示账号:陈明 `13800002233` / 密码 `Demo@12345` / 支付密码 `888888`。
- 环境变量坑:只换 Key 不换 `ZAI_BASE_URL` 会变成"DeepSeek 的 Key 打到智谱端点"的必挂组合
  (见 `AGENTS.md` 环境坑速查)。
- 前端启动不需要额外的数据库/缓存服务:Python 侧用 `data/bank.db`(SQLite),播种即得。

## 八、变更契约的正确姿势

契约**可以改**,但要按流程改——不能一个人顺手改掉:

- [ ] 1. **三处一起改**:`graph.py`(抛类型)→ `agent/api.py`(映射)→ `bank-parts.tsx`(渲染)
- [ ] 2. **同步本文件第三节的契约表**
- [ ] 3. 跑 `pytest tests/test_contract.py -q`,确认自动通过
- [ ] 4. 跑全量 `pytest tests -q`(133 个)
- [ ] 5. commit message 里写明"契约变更:xxx",并在 PR 里 @ 对方 review

只改一处时,**契约测试会直接失败并告诉你另一处该改什么**——这正是它存在的意义。
